### Native backdrop reuse decision (before implementation)

Retain `gpui_windows` as the native-window owner in the separately created Zui fork, pinned to the same original `0dc69aa` revision; do not patch Cargo's shared cache or add an external HWND manager. Reuse existing `set_window_composition_attribute` and `dwm_set_window_composition_attribute` plus the existing WM_ENTERSIZEMOVE/WM_EXITSIZEMOVE lifecycle. Add a per-window interactive-move flag while keeping the desired `background_appearance` unchanged. On legacy Windows use non-Acrylic blur-behind during moving/resizing, then restore the CURRENT desired appearance on exit; menus do not trigger suspension. On Windows 11 22621+ first use documented DWM transient-window Acrylic (3), with the legacy path as an API-failure fallback. Clear the other backdrop mechanism when switching, so Mica/Acrylic/opaque transitions do not retain a stale effect. Test policy and native transitions, including settings changes during a move, before claiming the lag fixed. This changes a verified problematic boundary rather than rewriting the UI, renderer, engine, terminal or sync.

### Harness boundary reuse decision (before implementation)

Actual Windows baseline harness library suite: 316 passed, 0 failed/ignored (`target/harness-baseline-tests.log`), so passing existing unit tests does not rule out the newly audited gaps. Existing business/process owners remain `crates/harness/src/process/windows`, `executable`, each provider driver and `shutdown_child`; no replacement agent runtime.

Source-proven gaps: `jsonrpc::read_loop` and child stderr drains use fallible UTF-8 `Lines` and terminate on one invalid byte; OpenCode attachment construction uses `format!("file://{path}")`; Windows process `prepare` hands npm batch shims (including canonical verbatim paths) to cmd.exe, whose command line/cwd constraints differ from native execution; Windows `shutdown_child` ignores its grace argument and kills immediately. Reuse the corresponding focused implementation/tests from upstream PR #977 at `02fddf0832283e3f5359951ed2d54e4d8593c6f2`, after checking current source compatibility. Select/adapt hunks, NOT the entire unmerged multi-provider rewrite. Preserve directory-header percent encoding (SDK behavior), ordinary custom batch fallback and strict argument validation; do not change provider auth, account routing, model choice or default shell. Exclude already-present probe/cache/installer improvements. Extend native fixture tests for invalid bytes, canonical npm shim launching/long arguments, safe file URL encoding and cooperative stdin-EOF/graceful teardown. No authenticated-provider success or data-corruption reproduction is claimed from source alone.

### Native teardown reuse decision (before implementation)

The unchanged official executable completed 3 isolated open/close cycles (exit 0 and stable device identity) using upstream `scripts/test-windows-lifecycle.ps1`, but ALL THREE runs logged `window not found`, invalid OLE/HWND errors, and `timed out waiting on app_will_quit`. Evidence directory: ignored `target/windows-lifecycle-3da0b584f2c04b05952a8d6c2be8ece7`. Therefore the existing script's PASS is incomplete acceptance; extend it to inspect errors and profile/session persistence.

Verified owner trace: native WM_DESTROY invokes GPUI close; dropping the GPUI window then schedules unconditional RevokeDragDrop/DestroyWindow on the same HWND. Keep ownership in `WindowsWindowState` with main-thread Cell flags, revoke registered OLE drop target ONCE while HWND is alive in WM_DESTROY, clear native callbacks before the removed GPUI window can receive late updates, and skip duplicate destruction after WM_DESTROY. Reuse the existing dispatcher queue; serialize dispatch-post versus platform-window shutdown rather than relying on a racy IsWindow/AtomicBool check alone. Do not drop !Send foreground runnables on a worker thread. `gpui::window` on_close already discards its missing-window error; do not edit that location just to suppress logs. The separate 200ms GPUI shutdown deadline is incompatible with Zeron's asynchronous engine drain: the existing on_quit callback immediately starts shutdown but first awaits a focus RPC to that same engine. Correct the ordering in the existing Tokio bridge (bounded focus notification, then shutdown) and add a per-App shutdown timeout setter to Zui with unchanged 200ms default for other callers; Zeron requests 30 seconds for its existing shutdown contract (auth refresh alone admits 10 seconds). The lifecycle probe must allow that bounded completion and require an explicit shutdown-complete log. This is not a claim that more waiting alone fixes the defect; verify actual engine cleanup, clean diagnostics and persistence, and investigate any remaining timeout rather than hiding it.

### Onboarding accessibility reuse decision (before implementation)

Scope the UIA finding to the actually observed welcome/appearance onboarding screens, not the whole application (many other components already declare roles). Local helpers `onboarding::{wide_button,quiet_link,primary,ghost}` have ids/clicks but no roles/tab stops, so a keyboard-only Windows user cannot reach the first-run actions and a screen reader cannot identify them. Reuse GPUI's existing `.role`, `.aria_label`, `.tab_index`, `.tab_stop`, focus styling and its built-in paired Enter/Space click synthesis (`gpui/src/elements/div.rs`); do not add a parallel key handler or redesign shared buttons. Annotate these local helpers and appearance choices; preserve disabled Continue behavior and add a real headless focus/activation regression using these same helpers. Native UIA recheck remains necessary when desktop-control infrastructure is stable.

### Engine space path deduplication reuse decision (before implementation)
